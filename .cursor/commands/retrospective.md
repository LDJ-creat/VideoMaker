# 会话复盘：提取问题、方案与技术决策

你是 VideoMaker 项目的技术文档作者。请**完整分析当前 Agent 会话的对话历史**（含用户诉求、排查过程、尝试过的方案、最终结论、相关代码改动），将**有长期价值**的内容整理成一份结构化复盘文档，写入项目 `docs/retrospectives/` 目录。

> 参考范例（结构与深度对齐，勿照抄内容）：@docs/retrospectives/2026-06-23-generation-cancel-retry-progress-session.md

---

## 1. 什么值得记录（筛选标准）

**必须记录**（满足任一即可）：

- 非显而易见的 **Bug / 故障**：有清晰现象、根因、修复方式
- **架构或设计决策**：在多个可行方案中做了选择，且选择理由对后人重要
- **踩坑与反模式**：「看起来能 work 但实际不行」的经验
- **跨模块链路问题**：API / Worker / Web / Composition 之间的协作边界
- **配置、运维、排障清单**：环境变量、进程生命周期、状态一致性等
- **测试与验证路径**：证明修复有效的命令或 E2E 步骤

**不要记录**：

- 纯机械操作（格式化、改 typo、单纯跑通已有流程）
- 尚未收敛的猜测（标为「待验证」时可简短列入遗留项，勿写成已解决）
- 与项目无关的闲聊
- 大段复制粘贴的代码（用文件路径 + 符号名引用即可）

若本次会话**没有**达到上述「值得记录」的门槛，**不要强行凑文档**——直接告知用户「本次会话暂无可沉淀的复盘内容」，并简要说明原因。

---

## 2. 信息来源（按优先级）

1. **当前会话全文**：用户问题、你的推理、工具输出摘要、最终结论
2. **本会话中实际修改的文件**：结合 diff 理解「改了什么、为什么」
3. **相关计划 / 规范**（仅在会话中涉及时引用）：`AGENTS.md`、`docs/superpowers/plans/` 等
4. **Git 状态**（可选）：若会话含提交，可在文末列出关联 commit；**不要自动 commit**

不要虚构未在会话中出现的文件路径、现象或 commit hash。

---

## 3. 输出文件

### 路径与命名

- 目录：`docs/retrospectives/`（不存在则创建）
- 文件名：`YYYY-MM-DD-<英文-kebab-主题>-session.md`
  - 日期：今天（本地日期）
  - 主题：2–5 个英文单词，概括会话核心（如 `generation-cancel-retry-progress`）
- **若同名文件已存在**：在文件名后加 `-2`、`-3`，或若明确是**同一会话的续篇**，可在文末追加「续篇」章节而非覆盖——**禁止静默覆盖**已有复盘

### 写入方式

- 使用 Write 工具创建新文件（或 StrReplace 追加续篇，需说明原因）
- 全文使用**中文**，技术术语、路径、符号名保持英文
- Markdown 格式，便于 Git  diff 与后续检索

## 5. 质量要求

- **准确**：现象、根因、方案三者逻辑闭环；不确定处标注「推测」或「待验证」
- **可检索**：标题和小节名用具体名词（模块名、文件名、API 路径），避免「问题一」「解决方案」等空泛命名
- **可复用**：后人不看会话记录也能按文档排障或答面试题
- **克制**：宁可少写也不要注水；单篇建议 150–400 行，复杂会话可更长
- **不重复**：若与 `docs/retrospectives/` 已有文档高度重复，指出关联文档并只记录**增量**（新根因、新修复、新决策）

## 6. 完成后回复用户

用简短中文总结：

1. 文档路径
2. 本会话沉淀了几个问题 / 决策（一行列表）
3. 若跳过写文档，说明原因

**不要**主动 git commit；用户若需提交，会使用 `/commit` 或其他方式。
