## 1. 我们在解决什么问题

### 1.1 改片前，用户能看到的问题

| 用户侧现象 | 通俗解释 |
|------------|----------|
| 改片后画面仍是「线条占位」，没有金句 | 分镜规格里只有骨架动画块，没有可读文案 |
| 工作台长期显示「Agent 审阅不可用（已豁免）」 | 机器审片没跑成，系统允许人工放行 |
| 明明要求重新生成，产物却像没改 | 分镜规格的指纹（哈希）没变，等于静默复用了旧稿 |
| Cursor 大量读仓库 Python、走测试用 lint 捷径 | 绕开正式文案校验与 HyperFrames 检查 |

### 1.2 根因归纳（五条）

1. **允许上屏的文案没有交给分镜 Agent**  
   改片时没有把分镜脚本里的金句整理成「白名单」，Agent 不知道哪些字可以出现在画面上。

2. **ACP 会话结束后收片条件太松**  
   即使 Agent 没真正改规格，Worker 仍可能把旧的或半成品规格当作结果收下。

3. **改片前临时目录没清干净**  
   上次 lint 草稿、审片标记等残留，干扰「这次算不算有效交卷」的判断。

4. **提示词与工具约束不够硬**  
   系统提示过长；测试模式 lint 可被 Agent 自行打开；修复提示里没有明确禁止读源码。

5. **「审阅不可用」容易被当成旧缓存**  
   有时是**这一次**会话里审片因基础设施失败被豁免，并非沿用上次的旧结论。

## 2. 我们做了什么（2026-07-06 已落地）

### 2.1 第一阶段：上屏文案策略

**目标**：改片时明确「哪些字可以出现在画面上」。

- 从分镜脚本、创作说明里的引号短语、包装层文案等，自动整理**允许上屏文案列表**。
- 改片准备阶段把该列表写入任务说明与创作契约，并同步到 ACP 的 task 配置。
- 素材生成管线在改片场景下再次合并文案策略，并记录「改前规格指纹」，要求**必须产出与改前不同的新规格**。
- 向 Agent 下发任务时：改片模式不再塞入完整旧规格（避免照抄），只给契约与指纹。
- 文案校验：只允许白名单内的文字上屏；若白名单为空则给出可操作的修复提示。

**主要代码位置**（需深入时再看）：Worker 侧 `display_copy_policy`、`material_slot_revise`；Composition 侧 `payload`、文案 guard。

### 2.2 第二阶段：防止「静默复用旧稿」（ACP 收片）

**目标**：Agent 交卷后，Worker 必须验收，不合格不收。

- 改片重跑前**清空** ACP  scratch 里的 lint 草稿、旧审片标记、旧规格等。
- 新增收片验收：规格指纹未变、交卷异常退出、改片场景下的半成品 harvest —— 一律拒绝。
- 改片场景禁止「部分 harvest」静默过关。

### 2.3 第三阶段：MCP 与提示词加固

**目标**：Agent 只走正式工具链，少探索、少走捷径。

- 使用**精简版系统提示**，最前面放硬性 STOP 规则（禁止读源码、禁止测试 lint 等）。
- 测试专用 lint 环境变量仅在 CI/测试模式注入，生产 ACP 子进程拿不到。
- MCP lint 单次最长 90 秒，超时失败。
- 会话内修复提示结构化：标明问题类型，并明确禁止读仓库源码。

## 4. 为什么工作台仍显示「Agent 审阅不可用」

### 4.1 不是用了旧的审片缓存

- 审片标记文件的写入时间与本次改片同一时刻（11:15 左右）。
- 标记里的规格指纹已是**改片后的新值**。
- 报告标明审片结论来自**本次会话内**流程，不是跳过审片直接复用旧报告。

### 4.2 真实原因：第二轮视频审片撞上限流

第二轮调用火山方舟「视频理解」模型时，账号返回 **HTTP 429**：  
`doubao-seed-2-1-pro` 推理额度用尽（安全体验模式暂停服务）。

系统将 429 视为**基础设施故障**（不是画面创意不合格），于是：

- 标记为「审阅不可用」；
- 同时**豁免通过**，允许人工审片；
- 界面上显示「纯文本模式」类标签。

**容易误解的一点**：  
**第一轮视频审片其实是成功的**（约 2.5 分钟，指出文字重叠、长静态帧、卡片偏上等问题），并促使 Agent 做了第二轮修复。  
但第二轮失败后，**新标记覆盖了第一轮结论**，界面只剩「审阅不可用」。

同一次生成里的 slot-6 初生成时，视频审片是正常的（有评分），说明模型网关配置本身没问题——是**同一会话里第二次调用**触发了账号限流。

### 4.3 建议后续改进

- 基础设施失败（429/503 等）时，**保留上一轮成功的视频审片结论**，不要整份降级成「不可用 + 纯文本」。
- 可观测性日志里分镜编号有时写成泛称「slot」，应修正为「slot-5」等，方便排查。

## 5. 「读源码」和「不走 MCP 规范」占多少时间？

### 5.1 和「初次生成整个 slot-5」对比

初生成该分镜时总 wall 约 **66 分钟**，大致分布：

- Cursor 读代码、调工具：约 **38 分钟**
- Worker 视频/视觉审片：约 **28 分钟**（当时循环次数很多）
- HyperFrames 实际编码：**不到 1 分钟**

初生成时，**探索仓库 + Agent 编排**占一半以上；审片循环是第二大头；视频编码几乎可以忽略。

### 5.2 本次「门内改片」约 16 分钟

| 时间去向 | 占总时长 | 判断 |
|----------|----------|------|
| 预览渲染 + 审片 | 约 28% | 可预期；两轮修复下很难低于 4–5 分钟 |
| lint 脚本卡死 | 约 25–38% | **意外**；修掉可直接省 4–6 分钟 |
| 读文件、搜索、自写脚本 | 约 20–30% | 仍不少，但比初生成好（没有 14 次审片循环） |
| 纯创作（写 HTML/动效） | 约 15–25% | 必要成本 |

**直接回答常见问题**：

- **占不占时间？** 占。去掉卡死后，不规范探索大约还有 **3–7 分钟/次改片**。
- **和 lint 卡死比哪个更大？** **本次改片 session 里，lint 卡死 ≥ 读源码**。
- **和规范的关系？** Agent 自写 `_invoke_mcp.py` 这类脚本，既违反「只用 MCP 工具」的约定，又**直接造成最长一段阻塞**。规范不只是合规，也影响耗时。

### 5.3 本次 Cursor 典型「越界」行为

- 读了测试文件、MCP 处理器源码、skill 文件（明明已通过 skill_view 拿到内容仍读源文件）。
- 在 scratch 里自写 Python 脚本直接调 lint，而不是用 MCP 的「lint 草稿」工具。
- 用 Shell 列目录、多次 python 调辅助脚本。
- **正面**：已不再使用测试 lint 环境变量捷径（门控生效）。

## 6. 单分镜还能怎么进一步提速

与 [审片预算复盘](2026-07-06-acp-review-only-budget-and-prompt-hardening.md) 中的措施（审片单独计次、工作目录隔离等）**叠加**考虑。按优先级排列。

### 6.1 最高优先级：去掉意外浪费（预计每镜省 4–8 分钟）

**2026-07-06 已实施**（`docs/superpowers/plans/2026-07-06-acp-agent-hardening-plan.md`）：

| 做什么 | 状态 |
|--------|------|
| 禁止 scratch 里的自写 lint 脚本 | ✅ acceptance + scratch 清理 |
| lint 超时强杀 | ✅ 已有 90s |
| 限流时保留上一轮审片结论 | ⏳ 未做（单独计划） |
| Cursor 工作目录改到 scratch | ✅ `VIDEOMAKER_ACP_SPAWN_CWD=scratch` |

| 做什么 | 怎么做 | 预期效果 |
|--------|--------|----------|
| 禁止 scratch 里的自写 lint 脚本 | 收片验收发现 `_invoke_mcp.py` 等即失败；提示词强调只能用 MCP lint | 消除本次 4–6 分钟卡死 |
| lint 超时强杀 | 已有 90 秒上限； hung 子进程必须杀掉并返回明确错误 | 避免无限等待 |
| 限流时保留上一轮审片结论 | 第 N 轮因 429 失败 → 报告继承第 N−1 轮视频审片 + 标注「基础设施失败」 | UI 不误报；用户仍能看到首轮审片意见 |
| Cursor 工作目录改到 scratch | 默认只能看到当前分镜临时目录，减少读全仓库诱因 | 减少探索 |

### 6.2 次优先级：压缩 Worker 固定步骤（预计省 1–3 分钟/镜）

| 做什么 | 怎么做 | 预期效果 |
|--------|--------|----------|
| 预览渲染用「低档位」 | 可配置更低帧率/分辨率；预览与终片分离 | 单次约 1 分钟 → 目标 25–35 秒 |
| 修复轮复用预览缓存 | 若只改动效/CSS，尽量复用已渲染帧 | 第二轮渲染减半 |
| 短视频审片改用「抽帧」 | 6 秒以内预览优先抽关键帧审片，而非上传整段视频 | 单轮审片常可从 2.5 分钟降到 0.5–1 分钟 |
| 改片是否重复会话内审片 | 已有开关可关改片时的 in-session 审片，需产品确认策略 | 视场景减少 1–2 轮审片 |
| 字体/浏览器预热 | 同一次生成多镜共享 HyperFrames 字体缓存 | 每镜 shave 数秒到十几秒 |

### 6.3 再次：压缩 Agent 编排（预计省 2–5 分钟，需实测）

**2026-07-06 已部分实施：**

| 做什么 | 状态 |
|--------|------|
| 技能文档摘要内联 | ✅ `AUTHOR_BRIEF.md` + `SKILLS_SUMMARY.md` bootstrap |
| MCP `read_author_brief` / validate / lint_scratch_file | ✅ |
| 监控越界读文件 | ✅ `trace_policy`（2 次 repo Read → abort） |
| 审片 1 次 + repair 无再审 | ✅ 默认 cap=1 |

| 做什么 | 怎么做 | 预期效果 |
|--------|--------|----------|
| 技能文档摘要内联 | 首轮任务里附带 composition/visual 要点，少再读 SKILL 源文件 | 减少十几次 Read |
| 改片专用短提示 | 不列完整技能目录，只给文案契约 + 改片指令 + 版式约束 | 减 token 与探索 |
| 监控越界读文件 | trace 里读到 `services/`、`tests/` 则终止会话并重试 | 强约束，需防误杀 |
| 更快的外部 Agent 模型 | 配置更快的 Claude 档位 | 全局 Agent 时间下降 |
| lint 结果缓存 | 同规格指纹跳过重复 HyperFrames lint | 重复 lint 时省秒级到三十秒级 |

### 6.4 中长期架构选项

- **内部 ReAct 替代 Cursor ACP**：工具链相同，但无 Cursor 自带读文件；耗时可预期，失去 Cursor 多模态编排。
- **改片走「补丁」而非整镜重写**：只改文案/动效时结构化 patch + lint，缩短轮次。
- **审片异步化**：先出预览进人工门，审片后台跑（需与「finalize 不再调 LLM」架构对齐）。
- **分镜模板复用**：同类 slot 命中知识库 composition 模式，热启动骨架。

### 6.5 不建议优先做的

| 做法 | 原因 |
|------|------|
| 取消会话内审片 | 本次首轮视频审片直接驱动有效修复；省 2.5 分钟但质量回退 |
| 全部改成纯文本审片 | 抓不到重叠、静帧等视觉问题 |
| 只加长 ACP 超时 | 不解决卡死与探索，只掩盖 |

## 7. 建议实施顺序

1. **限流/503 时保留上一轮视频审片结论**，界面展示基础设施原因（体验 + 避免误判）。  
2. **禁止 scratch 自写 lint 脚本 + Cursor 工作目录隔离**（省 4–6 分钟意外 + 减探索）。  
3. **预览渲染低档位**（每轮省约 30–60 秒）。  
4. **复核改片是否默认跑两轮视频审片**（产品策略）。  
5. **短视频审片改抽帧**（每轮省约 1–1.5 分钟）。  
6. **改片短提示 / 技能摘要内联**（需 A/B 验证）。

## 8. 改片耗时合理目标（HyperFrames 合成类分镜）

| 场景 | 本次 slot-5 实测 | 合理目标 |
|------|------------------|----------|
| 一轮对话：lint 过、审片过 | 未走通 | **8–12 分钟** |
| 两轮：审片否 → 修复 → 再审通过 | 约 16 分钟（含 lint 卡死） | **12–15 分钟**（去掉卡死 + 预览优化后） |
| 两轮：第二轮审片因限流失败 | 约 16 分钟 + UI 误判 | **墙钟时间相近**，但 UI 应保留首轮审片结论 |

**经验下限**：两轮改片时，Worker 侧「两次预览 + 两次审片」大约 **4 分钟** 很难再压；Agent 创作视分镜复杂度通常还需 **5–10 分钟**。
